# Прогноз → задание → калибровка

Цикл, по которому любой опыт или задание исполнителю проходит один раз и правильно. Судья — заранее записанный порог и побайтная (или иная объективная) проверка, а не впечатление.

## 00. Опоры — до любого предложения или задания (5 минут, обязательно)
Большинство ошибок — повтор уже пройденного или работа по устаревшему документу. Поэтому сначала:
1. **Закрытое.** Прочитать список закрытых направлений проекта (ways-of-working / Closed avenues, GRAVEYARD). Совпало — не предлагать.
2. **Запланированное.** Найти в плане проекта (MASTER_PLAN, ROADMAP), нет ли уже этой задачи с гипотезами и порядком шагов. Есть — продолжать оттуда, а не начинать заново.
3. **Измеренное.** Найти в CALIBRATION / FACTS_LEDGER / журнале результатов уже снятые числа по теме. Прогноз строится на них.
4. **Правила.** Сверить формулировки с уже принятыми правилами проекта (например: каждое «в N раз» — с условиями и с плотностью рядом; формат читать из пишущего кода).
5. **Живое состояние, а не документ.** Ветки, теги, версии, чужие таблицы, что сейчас в main — проверить командой (`git ls-remote`, `git tag`, свежий файл), а не по записи недельной давности.
В задании исполнителю — строка «Опоры: что прочитано и что проверено вживую».

## 0. Перед началом — четыре ответа
1. **Решение.** Какое конкретное решение изменится от результата? Нет решения — опыт не начинать.
2. **Потребитель.** Кто (названный человек/проект) воспользуется результатом? Нет — это исследование, не «продукт».
3. **Образец.** Кто решает эту задачу лучше всех сейчас? Его механизм, его числа, наша разница. Сравнение — с лучшей альтернативой той же функции, а не со слабой.
4. **Прогноз.** Число из модели (не «вырастет», а «+8…12 %») и критерий, который убивает гипотезу. Перечислить, что известно до прогона (прошлые замеры, потолки железа), и проверить, что прогноз им не противоречит. Модель предсказывает ноль — прогон не нужен.

## 1. Записать до прогона (CALIBRATION)
- Гипотеза одной строкой, прогноз числом, критерий провала.
- Правило выбора следующего шага: «если PASS → X, если FAIL → Y».
- Механические правила исключения данных (нагрузка, сбой) — заранее, решение только по ним, не по результату.
- Коммит с этим текстом идёт первым, до любого замера.

## 2. Проверка метода до основного прогона
- **Положительный контроль:** одинаковый вход дважды → одинаковый выход.
- **Отрицательный контроль:** заведомо другой вход → прибор видит разницу; испорченный вход → ошибка, а не тихий мусор.
- **Известный ответ:** эталон, совпадающий с прошлым числом (иначе прогон недействителен).
- **Каждые ворота проверить на известном случае**, включая собственное влияние прибора (пример: процесс замера сам даёт нагрузку ≈1.0 — порог «loadavg > 1.0» срабатывал бы от себя).
- **Условия сравнения совпадают** (машина, версия, потоки, путь чтения). Не совпадают — переделать, а не оговаривать.

## 3. Прогон
- Чекпоинты, сохранение каждого куска сразу (push), возможность продолжить после обрыва.
- Все попытки сохраняются, включая отброшенные; в отчёте «N из M пересняты».
- Время мерить в эксклюзивном окне (общий замок), фон записывать в начале и конце.

## 4. Вердикт
- По исходным критериям. Принятое по ходу (новый порог, перенастройка) — отдельной строкой, задним числом условием не становится.
- Перенастройка после просмотра результата — новый этап разработки с новым прогнозом.
- Слово не выше доказательства: наблюдение (число + лог) → модель (проверена на данных вне подгонки) → закон (вторая машина, второй корпус, совпавший прогноз) → новизна (закон + поиск prior art с источниками).

## 5. Калибровка
- Одна строка: прогноз / факт / HIT или MISS.
- MISS разобрать: какое допущение модели было неверным (пример: «два писателя одного формата дают одинаковые байты» — не проверили параметры).
- Подтверждённый ноль — результат, а не неудача.

## 6. Где ломается чужой механизм
Когда чужой инструмент или правило ломается о нашу специфику — записать: где именно, при каком условии, и достроить. Это главный источник того, что никто не формулировал. Не обходить, не оговаривать — довести до причины (файл:строка, минимальное воспроизведение, правка).

## 7. Шаблон задания исполнителю
```
[АДРЕСАТ] ИМЯ-ЗАДАНИЯ | одна строка сути
Контекст: что уже известно (с хэшами/ссылками), почему задание.
Цель: логический конец задачи — что должно существовать в конце (не «шаг», а результат,
  по которому принимается решение).
CALIBRATION (коммитить первым, текст без изменений): гипотезы, прогноз числом,
  критерий провала, правило следующего шага.
Проверка метода до основного прогона: контроли, эталон, окружение.
Шаги: по порядку; условия остановки на каждом.
Правила исключения данных (механические).
Результат: файл/ветка/черновик PR; что наружу не отправлять.
Отчёт: STATUS / хэши / что проверено / NEED.
```
- Один адресат на задание, метка в начале ([СЕССИЯ], [HW], …).
- Внешние действия (посты, письма, PR чужим) — только по слову владельца.

## 8. Роли
- Кто предлагает — не судит. Контролёр проверяет независимо: пересобирает, пересчитывает по сырым данным, сверяет хэши.
- Заявление наружу — отдельная проверка чисел по логам.
- Решение — за владельцем проекта: факт и риск называются один раз.
