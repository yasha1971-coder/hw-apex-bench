# First-user and adoption audit — 2026-09-18

Scope: repository metadata, README generator, documentation, CLI dispatch,
qualification/native runner, CI and comparable public tools. No new codec
measurements, release, upstream changes or external outreach. This is an audit
and a bounded first-user cleanup, not a claim of industrial certification.

## Observed facts versus explanations

GitHub repository metadata reported zero stars and forks, creation on September9,
description `Compressed Access Benchmark`, no homepage field and no topics.
Only about nine days have elapsed. Visitor/referrer/clone analytics were not
available through the exposed connector; no conversion rate or causal explanation
of zero stars can be established. Stars are not independent successful users.

A search surfaced an existing ENCODE.SU announcement, but opening the thread
returned403. Its replies were not inspected. Do not infer silence, rejection or
positive reception, and do not post a duplicate announcement without checking it.

Working hypotheses, not measured causes: weak discovery metadata, an expensive
first example, no small self-contained comparison in README, and too much
implementation history before the adapter instructions increase first-run effort.
The historical genome table can also be mistaken for promotion of one codec.

## What is worth keeping

- Complete archive accounting, byte-exact qualification and retained provenance.
- Losses next to wins; zstd wins the historical region columns, ACE wins density.
- Existing external-style XZ adapter, capability-driven n/a and native region ABI.
- Separate evidence scopes, immutable435 records, Apache/CC BY licensing and DOI.
- Interactive exploration, static tables and an existing small correctness CI.

These support a concrete promise: help an engineer investigate the density,
region latency and decoded-work cost of a compressed byte-range workload.
They do not establish universal codec superiority, real disk/network query speed,
cross-machine invariant ratios or support for every genomic data model.

## External reality

[lzbench](https://github.com/inikep/lzbench) gives a direct input-file command,
build instructions and a broad platform/codec matrix. Compete by answering a
different workload question, not by matching its codec count or star count.
[TurboBench](https://github.com/powturbo/TurboBench) already discusses in-memory
measurement and benchmarking pitfalls; discipline alone is not unique.
[Hecate](https://arxiv.org/abs/2603.15390) and
[AGC](https://doi.org/10.1093/bioinformatics/btad097) are relevant to genomic
compressed access. Do not claim the field was empty before this repository.

Primary early audience: developers choosing or implementing compressed byte-range
access, including genomic-tool authors. Storage engineers are a second audience,
but real I/O and application query semantics need separate experiments. A student
can learn from AXES.md; that does not make students the initial contributor pool.

   `Compare compressed byte-range access: density, latency and decoded work.`,

2. Run the documented small path once on a clean Linux environment. Record time
   to first PASS, dependency failures and output discoverability. Fix failures
   before a new codec, a new large benchmark or a broad announcement.
3. Ask a small number of relevant maintainers for one concrete task: try the
   qualification command and report the first confusing step or missing workload.
   No stars-for-stars, mass mentions or superiority claims. Outreach requires
   explicit owner authorization; none was sent during this audit.
4. Use feedback to secure three independent successful runs and one external
   workload/adapter review. These are goals, not observed adoption or promises.
5. Publish one worked real-workload decision with commands and losses. Link back
   to the existing announcement if appropriate; do not spam multiple communities
   with the same broad claim. A new codec should answer that workload, not pad a list.

Owner workload: one short review/feedback session at a time. The assistant can
maintain scripts, audits and drafts; the owner chooses which external contacts
to approach and whether their problem is worth supporting. No parallel expansion
into several products, package ecosystems or unrelated codecs is needed.

## Measure adoption rather than assume it

Keep a dated owner-only tally: observed repository visitors/referrers if accessible,
reported first-run attempts, independent PASS receipts, actionable failures,
repeat users and external contributions. Separate owner/CI runs from community
reports. Do not treat clones as verified human users or stars as retained users.
No telemetry, tracking pixels or scheduled messages were introduced.

If people do not arrive, improve targeted distribution. If they arrive but cannot
run it, improve installation. If they can run it but do not return, investigate
whether the output helps a real decision. More marketing cannot substitute for
that distinction. Two weeks can guide iteration; it cannot guarantee traction.
